# Mission Control steers only through the pane's terminal and reads detail from version-gated files

Mission Control sends everything a person can say to a Mission as text to the Droid terminal session's pane. The planning conversation, plan approval, redirect, and resume all stay in Droid's own terminal interface. Orca makes no Mission API call, writes no Mission file, and offers no model pickers or per-worker kill. It reads a Mission in three layers. The terminal's `live` / `unverifiable` / `exited` verdict decides liveness. Hooks in the agent-status store decide activity, including the phase from the lead's open tool: `AskUser`, `ProposeMission`, or `StartMissionRun`. Droid's Mission files decide detail only: features, milestones, progress log, pause reason (when the files carry one), models, handoffs. They are read on the execution host, read-only, gated on the Droid floor, and tolerant of unknown fields and values. The files never say a Mission is running or exited, and when they cannot be read Mission Control shows the terminal and worker rows alone. We chose this because Droid publishes no way to drive a Mission outside its terminal, so the controls and the detail have to come from the two surfaces Orca can see.

## Considered Options

- **Published events first, files only as the fallback.** Rejected. The typed `mission_*` notifications exist only on a wire that is hosted by the process running the Mission, and nothing attaches to a terminal-hosted one. A structured Droid session loaded on the orchestrator would be a second writer (ADR 0007), and its effect on a running Mission was never observed. For an owned Mission, hooks are the published signal and the files are the only source of detail.
- **Hosting the planning conversation or plan approval in Mission Control or in a structured Droid session.** Rejected. On `stream-jsonrpc` the Mission tools are listed but the model cannot load them, and the `propose_mission` and `start_mission_run` permission flow is unpublished.
- **A Start Mission button that runs `droid exec --mission`.** Rejected. It is one-shot, needs `--auto high`, auto-approves the plan, and has no planning conversation. An automation does not start a Mission either (next option).
- **An automation that starts a Mission, through `droid exec --mission` or a `/missions` launch prompt.** Rejected. A schedule would spend Mission credits with nobody present: `--mission` auto-approves the plan, and `/missions` stops at the picker and, on a first run, at a credit warning Orca does not confirm. A Droid automation stays a Droid terminal session and has no `droid exec` run kind.
- **Reusing a pane that holds a Mission for an automation run.** Rejected. A reused run types its prompt into the pane's live agent, and after a Pause the lead reads `done`, so the prompt would redirect a paused Mission and spend credits unattended.
- **Pressing Enter on "Begin new mission" for the user, once or twice.** Rejected. Orca cannot tell the trust dialog, the picker, and the first-run credit panel apart, and no hook fires when the picker renders. A second Enter would confirm a credit warning for the user, which this ADR already refuses for Continue. One guarded Enter needs a Droid screen rule written against a captured transcript, and what Enter does in an onboarded profile was never observed. Adding it later is an Orca-side change with no wire change.
- **A confirm dialog before Start Mission.** Rejected. The launch costs nothing, and Droid shows its own credit warning on a first run.
- **Model pickers for orchestrator, worker, and validator.** Rejected. `model-settings.json` mirrors the choice and does not control it, Droid's own settings are a Droid-only config UI (ADR 0004), and the exec model flags apply only to `droid exec --mission`. Droid's `/missions` settings and `/model` change them.
- **A Pause button that sends an interrupt before it was measured.** Deferred, then adopted for Esc once the by-hand check ran (see Consequences). Ctrl+C is rejected as a pause key: one press only arms an exit, and two exit `droid`, the Mission's only process, which stops the whole Mission.
- **A confirm dialog before Pause, a one-tap Continue, or Pause on an `unverifiable` terminal.** Rejected. Continue resumes the same worker session, so a pause is cheap to undo. A one-tap Continue would send credit-spending text on its own. An `unverifiable` terminal already gets no Send message.
- **An interrupted verdict on the paused row.** Rejected. The status store reads hooks only and cannot tell a user pause from a limit pause, which is news the attention rules would demote. The word would also collide with an Interrupted Mission.
- **Per-worker kill through `droid.kill_worker_session`.** Rejected. It is typed but undocumented, its effect on Mission state is unknown, and workers run inside the terminal's process.
- **A Mission notification kind, or a stuck detector.** Rejected. A new kind is a wire change for mobile and web with no gain over the row state, and Droid defines stuck only as its pause reasons.
- **Client opt-in through `runtime.clientCapabilities.update`.** Rejected. The client starts the stream itself, so an older client never receives a message it cannot read.
- **Client polling.** Rejected. It resends the whole snapshot on every tick over the relay, where a stream sends one only when something changed.
- **The host computes the verdict, banner, and actions.** Rejected. Every client already holds the status row and the verdict, so one shared function derives the view for all of them, and the host sends file facts only.
- **Hook snapshots decide whether a worker is running in Mission Control.** Rejected. Mobile receives no child snapshots, and two rules would let one Mission read differently on a phone and on desktop.

## Consequences

- Mission Control is behind the Factory App in four ways, on purpose: no model dropdowns, Pause only on Droid 0.245.1 or newer, no per-worker kill, and no plan editing.
- A lead row shows "Droid is asking you" on `AskUser`, "Plan waiting for your approval" on `ProposeMission`, and working on `StartMissionRun`. Orca adds no notification kind: a pause, whether at a retry or iteration limit or on the user's request, reads plain `done` in the row with no interrupted verdict, and Mission Control carries the reason when the files have one.
- Start Mission opens a new Droid terminal session in the workspace in terminal mode, whatever the Chat UI switch or the Droid launch setting says, with `/missions` as the launch prompt. That opens Droid's Missions picker with "Begin new mission" focused and spends no credits (checked on 0.238.0, 0.245.0, and 0.247.0). Orca sends no keys. The user presses Enter on the row and answers any folder-trust or first-run credit panel in the terminal. Orca focuses the new terminal and adds no Droid trust preset. The empty state's Start Mission button carries one hint line ("Opens Droid's Missions menu in a new terminal. Missions can use significantly more credits than a regular Droid session.") and no confirm dialog.
- No Mission exists until the `mission-session` tag appears. Until then, Mission Control shows a waiting variant of its empty state for the terminal Start Mission launched: "Waiting for you in the terminal", the main button Open terminal, and Start Mission hidden. It has no spinner and no timeout. It ends at the first of: the tag appears, the row shows a turn with no tag, or the terminal exits. It lives in the desktop renderer only, so a reload falls back to the plain empty state.
- Resume focuses the terminal when the Mission is `live`. After an interruption it opens `droid --resume <orchestrator id>` and leaves "Continue the mission." unsent, because sending spends credits and Droid reconciles the files to `paused` when it loads the session.
- An interrupted Mission is one whose files say `running` while its terminal's `droid` is proven `exited`. Mission Control shows it as interrupted and resumable. A Mission whose files say `paused` while its terminal is `exited` (after two quick Ctrl+C) is a Paused Mission, not an Interrupted one: Mission Control reads "Paused" with "Droid exited. Resume to continue" and offers the same Resume. A Mission whose terminal is `unverifiable` shows its last known state with its age and asks before Resume.
- The reader links a terminal to its Mission through the lead session id (the Mission id is the orchestrator's session id on Droid 0.242.1) and the `mission-session` tag. The file shapes were observed on Droid 0.238.0 and 0.242.1.
- Status rows, states, and notifications reach mobile and web with no wire change. Worker rows (the hook-fed child snapshots) reach desktop and the web client only: the mobile worktree list and `worktree ps` carry none, so mobile's workers come from the Mission detail stream alone. The same shared function decides on every client that a worker is running: the Mission's raw state is `running`, the terminal's verdict is not `exited`, and the worker has started with no end time. Hook snapshots never decide it. Without Mission detail, desktop and web keep worker rows named "Droid agent <first 8 characters of the session id>" from the snapshots, and mobile shows the lead row and the "Mission detail unavailable" banner with no worker rows. Send message and Resume reach them through `terminal.send`. Mission detail reaches them as a stream, `droidMission.subscribeDetail`, one per terminal, under a new host capability `droid-mission.detail.v1`. A client opens it only when the host lists the capability and while a Mission view is visible, so it sends no client capability. The host sends a full snapshot of raw file facts (at most 256 KiB, at most once a second, log and handoff text clipped) with an optional `droidVersion`, and a host without the capability shows rows only. Start Mission and the worker transcript tail are desktop-only in the first version.
- Pause sends one Esc (`\x1b`) to the Mission's terminal through `terminal.send`, in one write with no Enter and no status guard, and never Ctrl+C. On Droid 0.245.1 one Esc paused a running Mission in about a second, kept `droid` alive, and stopped the running worker or validator. A second Esc 300 ms later changed nothing, and Continue resumed the same worker session. There is no confirm dialog, and the button stays disabled until the Mission reads paused, with a short timeout.
- Pause is offered only for an owned Mission whose terminal is `live`, whose lead row's open tool is `StartMissionRun` (the one state measured), and whose host Droid is a stable release at or above 0.245.1, read from the snapshot's `droidVersion`. Everywhere else Mission Control keeps the hint "Pause is in the terminal": `AskUser` and `ProposeMission` (Esc may cancel the dialog), the orchestrator's own turn, `unverifiable` and `exited` terminals, observed Missions, a host without `droid-mission.detail.v1`, and an older Droid. This gate is separate from the Droid floor, and a by-hand Esc run on 0.238.0 and 0.244.0 can lower it.
- After a pause the lead fires `Stop` and only the interrupted worker or validator fires `idle_prompt`, so the child's snapshot goes and the row reads `done` (ADR 0005). Mission Control reads "Paused" from the files with the banner "Droid is waiting for you. Send a message to continue." A user pause records no reason in `state.json` or the progress log, so it names no cause. A reason line appears only when `mission_paused` carries a `pauseReason`, as a retry or iteration limit does. Send message opens pre-filled with "Continue the mission.", editable and unsent, because sending spends credits. The copy promises no redirect, since only that text was typed after a pause.
- While the row is working on `StartMissionRun`, a message typed with Enter queues under "Steering messages" and reaches the orchestrator when the run returns (118 s in the one run), not between tool calls. Send message then says "Droid reads this when the current run ends. Pause to stop the run first." It sends text and Enter, never Ctrl+Enter, which was not tried.
- An automation never starts a Mission and never passes `--mission`. If a Mission starts in an automation's pane anyway, it is an Owned Mission like any other. Reusing a live session, which only the desktop does, skips a Droid pane that Orca follows as an Owned Mission, running or paused, and launches a fresh pane. Which row field marks that pane is left to the build.
- Revisit this decision if Droid publishes a Mission control API, exposes `mission_*` notifications from a terminal-hosted Mission, or stops pausing a Mission on one Esc.
