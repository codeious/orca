# Owned Missions live in Droid terminal sessions and report as child work

Orca owns a Mission only while it runs in a Droid terminal session in an Orca pane, however it was started. The terminal owner that already exists on that host keeps it alive: the terminal daemon for local and WSL, the relay for SSH, and `orcad` on managed hosts. Orca adds no Mission supervisor of its own. The Mission's liveness is the `live` / `unverifiable` / `exited` verdict of its terminal's `droid` process. Its Mission workers, validators, and their subagents are child sessions: flat `subagents` snapshots on that terminal's row in the one agent-status store, written by the pane's hook listener from each child's own events, while only the pane's lead session sets the row's state, prompt, tool, and resume identity. Missions Orca does not run are observed Missions: read-only, `unverifiable` until Droid says they are completed, and absent from the status store. We chose this because on Droid 0.238.0 an interactive Mission is one process: the TUI `droid` runs every worker and validator inside it, creates no worktree, and commits on the working directory's current branch. `stream-jsonrpc` cannot start a Mission, and Mission files store no pid.

## Considered Options

- **An Orca-supervised `droid exec --mission` child.** Rejected. It is a one-shot run that auto-approves the plan and has no planning conversation. A child of app main is also stopped on quit, as structured sessions are.
- **Supervising Missions through `droid daemon`.** Rejected for the reasons in ADR 0001: it is undocumented, shared with the Factory App, and restarted by Droid's auto-update.
- **A structured Droid session as the Mission's process.** Not possible on 0.238.0, because `stream-jsonrpc` cannot start a Mission.
- **A `mission` row kind in the status store, keyed by Mission id.** Rejected. One `droid` process would show as two rows with two verdicts, and every reader would need a new kind.
- **Writing worker records from the Mission reader.** Rejected. Workers would stay invisible until the reader links the Mission, it needs a new provenance and a relay capability, and plain `Task` subagents would still need the hook path.
- **Nesting a validator's subagents under it.** Deferred. The hook lane's snapshot has no parent field, so nesting is a shared-type change that older clients would flatten. It can return as an optional field.
- **Writing Mission feature names into a child snapshot's `description`.** Rejected. It would make the one status store depend on version-gated, undocumented Mission files, and no row may depend on the Mission detail stream, which only Mission views open.
- **An optional `subagents` field on the shared agent row, so `worktree ps --json` and mobile receive child rows.** Rejected. Child work is absent from both for every agent, so adding it is a cross-agent change, not a Droid one.
- **Linking a terminal to its Mission by working directory.** Rejected. Several Missions and several `droid` processes can share a directory, and a wrong link would steer or stop the wrong Mission. Orca links through the terminal's Droid session id and Droid's session metadata. A Mission it cannot link is observed.
- **Desktop reading remote Mission files over the SSH file provider.** Rejected. It polls across the network and takes execution state off the execution host.
- **An Orca worktree per Mission or per worker.** Rejected. Droid never uses one. A user who wants isolation starts the Mission in a new Orca worktree through the normal flow.
- **Replacing the lead on every start without `calling_session_id`, including one that names the lead's own id.** Rejected for rows with a captured process identity: a repeat start from the owner process would blank a running Mission's worker rows. Kept for rows with no identity, where a relaunch of the same session cannot be told from a repeat.
- **Leaving the row `working` after an Esc pause, or clearing every child on a lead `Stop` while `StartMissionRun` is open.** Rejected. The first shows a stopped Mission as running until Continue. The second assumes the tool stays open at a pause, which was not observed, and a background child legitimately outlives a lead `Stop`. The child's own `idle_prompt` is the signal that was measured.

## Consequences

- Quitting Orca or installing an update leaves a Mission running. Closing its terminal or putting it to sleep by hand asks for confirmation while the Mission is in progress. Automatic sleep skips that terminal, and removing a workspace warns without blocking. Desktop, mobile, and web read the in-progress fact from the host's store, so they all warn the same way.
- When the terminal's process is proven `exited`, its workers are `exited` only if the host's Droid is at or above Orca's Droid floor. Otherwise they stay `unverifiable`. Raising the floor means checking in-process hosting again by hand, because a Mission spends credits and cannot run in automated tests.
- The terminal's `live` / `unverifiable` / `exited` verdict does not exist for a Droid terminal yet: only Claude's hooks capture the agent's process identity, so a Droid row has none. Droid hooks must capture it first, and until then the verdict is `unverifiable` (ADR 0007).
- The pane's lead session is the session of its latest `SessionStart` with no `calling_session_id`, taken only from a hook of the row's owner process. A start from the owner process that names the lead's own session id is a repeat and changes nothing: not the row, the pane's prompt and tool cache, the child snapshots, the finished-child marks, or `restoredUnconfirmed`. Only a start that changes the lead clears the pane's caches. A row with no captured process identity (Windows, rows saved before the capture) has no owner process to compare, and a relaunched `droid --resume <id>` sends the same payload as `/resume <id of the current session>` (`source=resume`, the same id, neither `previous_session_id` nor `calling_session_id`; seen on 0.238.0 and 0.244.0). So there a start naming the lead's own id replaces the lead. The cost is that `/resume <current id>` drops a live Mission's worker snapshots, and they stay dropped because an unseen session without a parent is not adopted. The alternative would leave a dead process's children holding the row `working`. A hook from any other process never chooses or replaces the lead: a `droid exec` the lead runs in the pane, or a relaunched `droid` whose predecessor's exit was not seen. It triggers the existing owner check instead, and once the owner is proven `exited` the next event from the new process starts a fresh provisional lead. A missing `SessionStart` needs no other handling, because the lead's start makes no row and every hook carries the session id and the process identity. Only the lead's events set the row's state, prompt, tool, and resume identity, and a child's `SessionStart` no longer clears the pane's caches.
- A session whose start names a `calling_session_id` is a child. Its `SessionStart` records the child id and its parent and creates no snapshot, and a repeat changes nothing. Its prompt and tool events update its own snapshot only: they mean `working`, and a `permission_prompt` `Notification` means `waiting`. Its `Stop`, or its own `SessionEnd`, removes the snapshot and marks the id finished, and a later `SessionStart` that names a `calling_session_id` for a finished id is ignored. A start with none that names a finished child's id replaces the lead like any other new id. One code path reads Droid 0.238.0, where a child fires no `SessionEnd`, and 0.244.0, where it fires a second `SessionStart` and a `SessionEnd reason=other` after its `Stop`. A child's `SessionEnd` never touches the process verdict (ADR 0007). A child's `PreToolUse` is never `waiting`, because workers run at `auto-high` and do not ask. `SubagentStop`, which carries the lead's session id, and child `Notification`s other than `permission_prompt` and `idle_prompt` are dropped. A child's `idle_prompt` means it is waiting for the user, not working, so it removes that child's snapshot without marking the id finished. The child's next prompt or tool event brings the snapshot back, because the listener keeps its recorded parent. This is how an Esc pause reads: the lead fires `Stop`, the interrupted worker or validator fires `idle_prompt` and then no `Stop` or `SessionEnd` until Continue, and the row reads `done` with no working child left.
- The lead's idle `Notification`, Droid's signal after a user interrupt, drops the child snapshots that were running in the lead's open turn, because an interrupted Mission's workers may never send a `Stop`. A lead `Stop` keeps its children, and a child that outlived a `Stop` (a background child) survives a later idle `Notification`, because the user did not interrupt it. A row is not `done` while a child is `working`, and while `StartMissionRun` is open the row shows `working` on that tool, because the lead sends no other event during a run. When a background child's `Stop` leaves no child working while the lead is stopped, the row stays `working` until the lead's next hook or 10 s, whichever comes first, because the lead wakes with an unprompted `UserPromptSubmit` (0.6 s later in the one run observed). A child that ends with neither `Stop` nor `SessionEnd` holds the row `working` until the lead exits or is replaced. A Mission worker or validator paused by Esc is not this case, because its `idle_prompt` removes its snapshot. The hooks of a paused validator's reviewer subagents were not examined, and they may still hold the row `working`.
- After a restart the lead is seeded from the restored row's resume identity. With none, the first session seen is a provisional lead, and a `calling_session_id` naming another session repoints the lead to the root of its chain. Once a lead is known, an unseen session without a parent is not adopted. A start with no `calling_session_id` that names a different session (a resume, `/new`, `/tree`) replaces the old lead and drops its children. One that names the lead's own id, including the id the lead was seeded with, is a repeat. A process exit clears the lead. There is no guard against replacement while the lead is mid-turn: every plain `Task` subagent `SessionStart` observed, foreground and background, on Droid 0.238.0 and 0.244.0, carried `calling_session_id` naming the session that spawned it, so a start without one always replaces the lead. `/new` and `/clear` fire a `SessionStart` with `source` `resume`, a new id, and neither `calling_session_id` nor `previous_session_id`. `/tree` and, on 0.244.0, `/resume <id>` switch sessions in the same process the same way, except that the start carries `previous_session_id` (the new session's fork parent, not always the session just left), no `SessionEnd reason=clear` comes first, and the old session's `SessionEnd reason=other` follows the new start. `/resume <id of the pane's current session>` on 0.244.0 fires a lone `SessionStart` (`source=resume`) with neither `previous_session_id` nor `calling_session_id` and no `SessionEnd`: a repeat. `/fork` and an empty `/sessions` picker switch nothing.
- Child snapshots are flat siblings under the terminal's row. The parent link from `calling_session_id` stays in the listener and the Mission reader. Hooks carry no worker name, and the status store never holds a Mission name, so every row is built from hooks alone. The listener gives each child `agentType: 'droid'` and `description: 'Droid agent <first 8 characters of its session id>'`, so the sidebar, the dashboard rows, the dashboard pop-out, and older clients read the same text. No row says Worker, Validator, or Subagent, because hooks cannot tell them apart. Feature names and kinds appear only in Mission Control, joined by session id.
- Child rows follow the existing rules: the sidebar and dashboard list running children only, so a finished worker leaves and its history is Mission Control's, and a child under a parent Orca no longer hears from, such as behind an unreachable SSH relay, reads "No recent update" instead of disappearing.
- Status rows need no new provenance and no wire change, but child rows reach only desktop and the web client, which runs the desktop renderer. `worktree ps` (human and `--json`) and the mobile worktree list carry one row per pane and no child rows, for every agent. The Mission reader's relay message, for Mission Control detail, is negotiated as a capability. A host without it shows the terminal row, and on desktop and web its child rows, but no Mission detail.
- Resume has one writer at a time. A `live` Mission's terminal is focused. An `exited` or completed Mission resumes in a new Droid terminal session on its own host, in the workspace that matches its working directory. An `unverifiable` Mission, or an observed one that is not finished, needs confirmation first.
- Droid's `-w` checkouts stay external worktrees. Orca never deletes Droid's checkouts, branches, Mission directories, or sessions.
- Revisit this decision if Droid can start a Mission over `stream-jsonrpc`, or runs workers as separate processes.
