# Droid config surfaces

## Question

For MCP servers, skills, hooks, plugins, custom droids, slash commands, settings layers (including org-managed settings), and permission rules: where does each live, what is the file format, which `droid` subcommands and `droid.*` RPC methods read or write it, and who else writes it? Where can that collide with Orca's hook installer (`~/.factory/settings.json`) and skill installer (`.factory/skills`)?

## Short answer

Droid's programmable config is mostly JSON under `~/.factory/` (user) and `<repo>/.factory/` (project), plus nested folder `.factory/` directories and an org layer that users cannot weaken. MCP servers are `mcp.json`; skills, droids, and slash commands are Markdown trees; hooks are `hooks.json` or a `hooks` key in `settings.json`; plugins, permission rules, and almost every other preference are keys in `settings.json`.

The CLI that writes config is only `droid mcp` (user `mcp.json`) and `droid plugin` (user or project scope). `droid rules check` is read-only. There is no `droid skills`, `droid hooks`, `droid droids`, or `droid commands` subcommand in Droid 0.238.0. The exec JSON-RPC namespace `droid.*` can list and mutate MCP servers and skill enablement, and can list slash commands. It cannot register hooks, droids, plugins, or permission rules. A parallel `daemon.*` namespace in `@factory/droid-sdk@0.9.1` adds plugin install and raw MCP-config get/update.

Orca's hook installer rewrites the whole user `settings.json` `hooks` object. Droid's `/hooks` UI writes `hooks.json` instead, and the docs read the `settings.json` `hooks` key only when `hooks.json` is absent. Orca's skill installer copies into the same `~/.factory/skills` and `<workspace>/.factory/skills` trees Droid discovers, where a same-name project skill wins over personal and plugin skills.

## Findings

Versions checked: Droid CLI `0.238.0` (`droid --version`). TypeScript SDK `@factory/droid-sdk@0.9.1`, unpacked with `npm pack` into a temp directory, not the repo. Python SDK cited from the docs only (`pip install droid-sdk`, import `droid_sdk`); its package was not unpacked.

### CLI and RPC inventory

`droid --help` on 0.238.0 lists `resume`, `exec`, `daemon`, `search|find`, `update`, `mcp`, `plugin`, `computer`, `doctor`. It does not list `rules`, `skills`, `hooks`, `droids`, or `commands`. `droid help skills` and `droid help hooks` exit 1 and reprint the root help. `droid mcp`, `droid plugin`, and `droid rules` have the subcommands in the evidence log. Global `--settings <path>` is "merged for this process only".

`DroidServerMethod` in `@factory/droid-sdk@0.9.1` (`package/dist/index-C06W9tbN.d.ts`) is the exec `droid.*` set. Config-related members:

- MCP: `droid.add_mcp_server`, `droid.remove_mcp_server`, `droid.toggle_mcp_server`, `droid.toggle_mcp_tool`, `droid.list_mcp_servers`, `droid.list_mcp_tools`, `droid.list_mcp_registry`, `droid.authenticate_mcp_server`, `droid.cancel_mcp_auth`, `droid.clear_mcp_auth`, `droid.submit_mcp_auth_code`, `droid.submit_mcp_auth_error`
- Skills: `droid.list_skills`, `droid.set_skill_disabled`
- Commands: `droid.list_commands` (no set/create)
- None for hooks, plugins, droids, permission rules, or a general settings write. `droid.update_session_settings` updates the live session (model, autonomy, tools), not the settings file

`McpSettingsLevel` in `package/dist/node.d.ts` is `SettingsLevel.User` only. `AddMcpServerRequestParamsSchema` fields are `name`, `type: "stdio"|"http"|"sse"`, optional `url`, `headers`, `oauth`, `command`, `args`, `env`. `SetSkillDisabledRequestParamsSchema` is `skillName`, `disabled`, optional `settingsLevel` `user` or `project`.

The same package's `DaemonDroidMethod` repeats those under `daemon.*` and adds `daemon.get_mcp_config`, `daemon.update_mcp_config`, plugin install/enable/marketplace methods, and `daemon.list_commands`. `DaemonSettingsMethod` is `daemon.get_default_settings`, `daemon.update_session_defaults`, and custom-model list/upsert/delete. `McpConfigSource` in that file is `"user" | "project"` only. The high-level docs page documents the session methods (`addMcpServer`, `removeMcpServer`, `toggleMcpServer`, `listMcpServers`, `listMcpTools`, `authenticateMcpServer`, `listSkills`, `setSkillDisabled`) and says hooks have no registration API. It does not document the `daemon.*` plugin methods.

Python session methods that mutate user MCP config: `add_mcp_server`, `remove_mcp_server`, `enable_mcp_server`, `disable_mcp_server`, `enable_mcp_tool`, `disable_mcp_tool`, plus auth helpers. The docs say remove/enable/disable "do not accept a project-scope argument" and that `SessionConfig.mcp_servers` are session-scoped. Skills: `list_skills`, `enable_skill`, `disable_skill`. Hooks: "There is no Python API for defining hooks."

### How org-managed settings override user and project config

Four authored levels share one schema: org, folder (`<git-root>/.../<subfolder>/.factory/`), project (`<git-root>/.factory/`), user (`~/.factory/`). Build order, highest priority first: Org, Runtime (`--settings`), Folder, Project, User, Dynamic, BuiltIn.

Org policy arrives from the managed-settings endpoint, an org `.factory/` bundle, or a system file that wins over the endpoint when present and valid:

| OS | System managed settings |
| --- | --- |
| macOS | `/Library/Application Support/Factory/settings.json` |
| Linux and WSL | `/etc/factory/settings.json` |
| Windows | `C:\Program Files\Factory\settings.json` |

A missing system file falls back to the endpoint. A present but invalid system file becomes an empty org policy, not a silent bypass.

Two precedence directions:

- Hard controls: highest level present wins. Lower levels may accumulate where the schema says so, and cannot weaken or remove. Examples: `modelPolicy`, `mcpPolicy`, `permissionRules` (and deprecated command lists), `sandbox`, managed `hooks`, `strictEnabledPlugins`, `strictKnownMarketplaces`, `subagentModelSettings`, `maxAutonomyLevel`, `subagentAutonomyLevel`, `allowManagedHooksOnly`, `webSearchDisabled` (org-only; user/project/folder values ignored).
- Session defaults: most-local wins (Runtime, then Folder, Project, User, Org, Dynamic, BuiltIn), still capped by hard controls. Keys inside `sessionDefaultSettings`, plus mission model/reasoning fields.

Merge modes that matter here:

- MCP server objects: locked keys. A lower level can add a new server name and cannot modify or delete a higher level's entry. `mcpPolicy`, when `enabled`, filters what may connect. Matching is hostname or stdio command/argument, not the server's configured name. An enabled policy with an empty allowlist blocks every server. Disallowed servers stay in `mcp.json` but do not connect. Users cannot override `mcpPolicy`.
- Hooks: org `hooks` always load unless `hooksDisabled` is set. Lower levels cannot remove them. `allowManagedHooksOnly: true` ignores user and project hooks (org hooks and org-enabled plugin hooks still load).
- Plugins: `enabledPlugins` merges additively across org, project, and user unless `strictEnabledPlugins` is true, in which case this level and higher are the exhaustive allowlist and lower enables are rejected. `strictKnownMarketplaces` is a ceiling; lower levels cannot broaden it. There is no local CLI to change org activation.
- Permission rules: not array-union. IDs resolve Org, Runtime, Folder, Project, User. A higher valid definition claims a repeated id (a disabled rule still claims it). Different ids accumulate, then `block` beats `ask` beats `allow`. `settings.local.json` precedes `settings.json` inside one folder. Project and folder rules require workspace trust. An empty rules array does not clear inherited rules. A native rule can replace a custom legacy restriction from the same source only; other sources still apply.
- Skills and droids: org-managed settings can outrank discovered skills, including an automation's own skills. The skills page does not list an org skills directory in its 1–5 precedence. Outside mission/automation sessions that precedence is folder and project skills, project plugin skills, personal skills, user plugin skills, built-ins. Same sanitized name inside one bucket is invalid. `disabledSkills` arrays from user and project are combined, so either disable wins. Custom droid files: project beats personal. Org controls on subagents (`subagentAutonomyLevel`, `maxAutonomyLevel`, `subagentModelSettings`, MCP policy) override user/project/folder and cannot be weakened; that is policy, not a documented org-droid file merge.

### Collision risks with Orca's installers

Hook installer (`src/main/droid/hook-service.ts`):

- Local path is `~/.factory/settings.json` (`getConfigPath`, line 60–62). Remote install writes `<remoteHome>/.factory/settings.json` (line 260). It does not write `hooks.json`.
- `install()` parses the whole file (`readHooksJson` → `JSON.parse` in `src/main/agent-hooks/hooks-json-read.ts:15-20`), replaces `config.hooks` (`buildInstalledDroidConfig`, lines 152–162), and `writeHooksJson` stringifies that entire object (`installer-utils.ts:299`). `remove()` does the same. Any other key in that file (`disabledSkills`, `enabledPlugins`, `permissionRules`, `customModels`, `sessionDefaultSettings`, `extraKnownMarketplaces`) is rewritten from the in-memory copy. A `/settings` save or `droid.set_skill_disabled` between the read and the write can be lost. The writer skips the write when the serialized bytes already match, and rotates a backup when they do not.
- Events it installs: `SessionStart`, `UserPromptSubmit`, `Stop`, `SubagentStop`, `PreToolUse` matcher `*`, `PostToolUse` matcher `*`, `PermissionRequest` matcher `*`, `Notification` (lines 36–58). It leaves non-managed hook commands in place and only strips commands whose path contains its `agent-hooks/droid-hook` script. It does not set `hooksDisabled`.
- Published `/hooks` saves user or project `hooks.json`, not the `settings.json` key. Docs: if `hooks.json` is absent, Droid reads the `hooks` key. On this machine `~/.factory/hooks.json` was absent, so the settings key is the documented user source. Creating `hooks.json` (the `/hooks` UI, or a native UI that follows it) is the documented way to stop reading Orca's settings key. Org `allowManagedHooksOnly` drops user and project hooks entirely, including Orca's. `hooksDisabled: true` disables every hook, which Orca's status already reports.
- `PermissionRequest` is not in the published event table or the org schema's event list ("Unknown event keys are tolerated but warned about"). Orca writes it anyway. Whether current Droid fires it is not in the docs.
- Plugin hooks and org hooks merge in addition to user hooks. They are not in `settings.json`, so Orca's rewrite does not see or remove them.

Skill installer:

- Droid provider roots are `['.factory', 'skills']` at both global and workspace scope (`src/shared/skill-install-providers.ts:56-61`). Destinations are `join(scopeRoot, ...segments)` (`src/main/skills/skill-provider-destinations.ts:45-49`), so `~/.factory/skills/<skill>` and `<workspace>/.factory/skills/<skill>`.
- Discovery scans those same paths (`src/main/skills/skill-discovery-sources.ts:160-167` and `247-254`) and also `.agents/skills` and `.agent/skills`, which this provider does not use as its Droid destination.
- A same-name skill in the project or folder `.factory/skills` tree overrides personal skills and both project and user plugin skills. Installing into `~/.factory/skills` overrides user plugin skills and built-ins, and loses to any project/folder skill of that name. Two copies in one bucket are invalid configuration.
- `/skills` and `droid.set_skill_disabled` do not delete the directory. They set `disabledSkills` in user or project `settings.json`. That is a second collision with the hook installer, because both write `~/.factory/settings.json`. A disable survives an Orca reinstall of the files. Orca's skill installer does not write `disabledSkills`.
- Plugin skills live inside the plugin cache, not `.factory/skills`, but they share the skill-name namespace.

Observed on this profile, names only, not a published contract: `~/.factory/settings.local.json` was absent. User `settings.json` contained `enabledPlugins`, `extraKnownMarketplaces`, `enableCustomDroids`, and `trustedFolders` in addition to published preference keys. `enableCustomDroids` and `trustedFolders` are not in the settings reference that was fetched. `~/.factory/org-managed-settings.cache.json` existed (keys `orgId`, `userId`, `managedSettings`, `factoryTier`, `revision`, `cachedAt`). The docs describe the endpoint and the system file, not this cache path.

## Unknowns and risks

- Docs say the `settings.json` `hooks` key is read when `hooks.json` is absent. They do not show a merge example with both files present. Treating `hooks.json` as a replacement is the reading the sentence supports, and it is the dangerous case for Orca, but it was not executed.
- `PermissionRequest` is written by Orca and present as a key in this profile's `settings.json`. It is not a published hook event. Firing behavior was not tested.
- `persistentPermissions` inside `mcp.json` was observed. The docs never name that key, and `droid mcp permissions` was not run (it can revoke). Binding the CLI to that key is an inference.
